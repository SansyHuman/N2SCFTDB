# SQLite character-cache validation — 2026-09-09

The SQLite candidate was implemented in temporary modules under `/tmp/sci-sqlite-cache/candidate` and compared with the unchanged JSON implementation from git revision `d4d103a` before replacement. Exact outputs agreed, and the new cache improved the larger cold workload and every measured warm workload. The replacement preserves the LiE decomposition and singlet algorithms; avoiding full decomposition on a cold singlet miss is a separate future optimization.

The default file is `char_decomposition_cache.db` at the project root. It contains `character_decompositions` and `singlet_coefficients`, with schema/convention version 1 in `PRAGMA user_version`. Coefficients use decimal strings for arbitrary-size signed integers. Keys retain actual conjugate orientations; character-product keys merge repeated labels and sort factors. Singlet lookup precedes decomposition lookup.

SQLite uses WAL, per-thread/per-process connections, a 30-second lock timeout with bounded busy retries, and short transactions for completed results. Sequential decomposition batches flush at 64 entries and on completion; parallel workers return results to the parent for writes at dependency-level boundaries. The default FULL synchronous setting is retained. No LiE calculation runs inside a write transaction.

**Measurement method.** Local Sage Python 3.11.16, SQLite 3.53.4, installed FORM and LiE. Tables show medians of three trials with one decomposition worker. Backend order alternated. Every trial started with a different, empty application-cache directory; its warm pass reopened the saved cache in a new client. OS filesystem caches were not flushed. Imports and initial Sage Lie-algebra construction were excluded. Exact coefficient dictionaries were compared after every run, rather than comparing only formatted strings. Raw timings are in `sqlite_cache_timings.json`.

**Complete A8 SQCD index through t^18.** This includes ordinary input validation, FORM expansion, parsing, projection, polynomial assembly, and cache closure, with Sage algebra objects already initialized.

Some short cold calculations are 30–50 ms slower, principally because a new SQLite database needs initialization and durable commits. The migration is not a universal cold-run speedup. Warm projection runs make zero LiE calls. FORM expansion is still required for complete index calculations, so complete-index speedups are smaller than projection speedups.

**Correctness and compatibility.**

- All 84 projection evaluations (seven cases × three trials × two backends × two cache states) produced matching exact index coefficients.
- All 2,343 SQLite decomposition rows from those trials matched the original JSON decompositions individually.
- Fifty additional decompositions and sixty singlet queries matched across A1, A2, B2, C3, D4, D5, E6, E7, F4 and G2.
- All thirteen existing index tests passed against the temporary candidate before replacement.
- The full suite after replacement ran 164 tests: 162 passed and the two existing live-MySQL tests were skipped.
- At the time of this benchmark, regression tests covered independent SU(2) weight expansion, signed and very large coefficients, empty decompositions, cached zero/negative singlets, exact conjugate orientation, product ordering, concurrent threads and independent processes, reopening, unavailable LiE on cache hits, failure handling, schema version rejection and legacy JSON import.
- A default-path smoke check created the root database, verified `PRAGMA integrity_check = ok`, and reproduced an index with LiE unavailable. An explicit database path gave the same index.

After this benchmark, the legacy JSON importer, directory discovery and obsolete `cache_path()` helper were removed at the user's request. Lookup now uses only memory and SQLite, calculating missing entries with LiE. The cleanup passed 163 tests (161 passed, two existing live-MySQL skips); it removes the obsolete import test and leaves the SQLite schema unchanged. The timings above describe the initial SQLite implementation.

The standalone character cache retains `cache_directory=` for a directory and `database_path=` for a file, with mutually exclusive builder CLI options `--cache-directory` and `--cache-database`. As of 15 September 2026, index calculation instead uses `char_cache_database_path=` / `--char-cache-database` for a file. The property calculator and standalone index API share the root default. The reproduction script adapts the current API while retaining the historical baseline's original directory argument.

**Reproduction.** Run `test/benchmark_character_cache.py` with Sage Python, an unused `--output-directory`, and `--suite full`, `--suite decomposition` or `--suite projection`. The default `--baseline-ref d4d103a` loads the previous implementation from git into temporary modules without checking out or modifying the repository. `--rounds 3 --workers 1` reproduces the protocol above. Timings depend on the machine and filesystem; they are not performance guarantees.
